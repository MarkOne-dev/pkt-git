# Collaborative Workflow

This document is the team SOP. It covers the day-to-day loop, what the hooks do
automatically, branching and Pull Requests, and the rules for conflict
resolution.

## The One-Command Model

Install the `pkt` binary once per machine, then wire any repository with one
command:

```bash
pkt init
```

`pkt init` writes three thin POSIX shell hooks into `.githooks/`, records the
absolute path of the running binary in repository-local `pktgit.bin`, activates
the hooks with `core.hooksPath`, and merges the required rules into
`.gitattributes`. There is no Python, virtualenv, template copy, or per-repo
tool installation.

To import a project that already exists on disk, simply run:

```bash
pkt init
```

If an existing `.pkt` or `.pka` file is detected in the repository, `pkt init` automatically generates the initial snapshot in `snapshot/<project>/`. Then save to Git:

```bash
git add .
git commit -m "chore: import PT project"
```

You can also export manually anytime using convention-based paths:

```bash
pkt export my_project.pkt             # destination defaults to snapshot/my_project/
pkt export                            # auto-detects the topology in the repository
```

## What `pkt init` Actually Does

The hooks are deliberately thin:

```sh
#!/bin/sh
# Generated by pkt init. Do not edit.
exec "$(git config --get pktgit.bin || command -v pkt)" pre-commit "$@"
```

The `post-merge` and `post-checkout` hooks use the same pattern with their own
command name. Consequences:

- Repositories carry no copy of the tool; one binary install serves every
  project, and upgrades take effect everywhere.
- Automation is repository-local. `pkt init` never changes global Git
  configuration and never affects other repositories.
- Moving the binary requires rerunning `pkt init` in each repository so
  `pktgit.bin` points at the new absolute path.

## The Daily Loop

### Saving your work

```bash
# 1. Edit the network in Packet Tracer, then Ctrl+S.
# 2. From the repository:
git add .
git commit -m "feat: add VLAN 60 to SW_ACC_ADMIN_PUNO"
git push
```

The **pre-commit** hook guarantees that every commit containing a `.pkt` or
`.pka` also contains its freshly generated textual snapshot:

1. Detects staged `.pkt`/`.pka` files (added, copied, modified, or renamed).
2. Runs the Go exporter for each one into `snapshot/<project>/`.
3. Stages the regenerated XML, `.cfg` files, and `topology.json`.
4. Warns if a snapshot changed without its binary; the commit is still valid,
   but the binary is stale and must be rebuilt.

If an export fails, the hook aborts the commit and does not stage a partial
snapshot. A broken binary cannot be committed silently.

### Receiving work

```bash
git pull        # or git merge, or git checkout of a branch
```

The **post-merge** and **post-checkout** hooks:

1. Determine which `snapshot/*/base.snapshot.xml` files changed.
   - Normal merge: `ORIG_HEAD..HEAD`, with `HEAD^..HEAD` and root-commit
     fallbacks.
   - Squash merge: the staged index, because `HEAD` does not move.
   - Checkout: the old and new revisions, only when the branch flag is `1`.
2. Run the Go builder for each changed project.
3. Atomically write `topologia/<project>.pkt` and report the rebuilt path.

A failed rebuild is reported and makes the hook exit non-zero, but it does not
abort the merge or checkout. The snapshot remains the source of truth.

The two directions are mirror images:

| Event | Hook | Action |
|---|---|---|
| `.pkt`/`.pka` staged | pre-commit | export → snapshot staged with it |
| snapshot arrives via merge/pull | post-merge | build → local `.pkt` rebuilt |
| branch switch changes snapshot | post-checkout | build → local `.pkt` rebuilt |

If you only use this conventional workflow, you never run `export` or `build`
yourself. They are hook automation.

## Branching and Pull Requests

```bash
git switch -c feature/vlans-mario
git switch -c feature/routing-vanessa
```

Both branches can develop in parallel because the textual snapshots merge
semantically: OSPF config lines and VLAN assignment lines touch different
devices/files, so Git merges them cleanly. Binary `.pkt` files are treated as
binary and never auto-merged; text decides.

On GitHub:

1. Push the feature branch and open a Pull Request.
2. Reviewers see the network as text diffs: every IP, VLAN, and ACL line with
   `+`/`-` markers, reviewable without opening Packet Tracer.
3. After merge, teammates run `git pull`; the hook rebuilds their local
   binaries.

## Conflict Resolution

When two branches edit the same config line (for example, VLAN 50 versus VLAN
60 on `SW_ACC_ADMIN_PUNO` `FastEthernet0/3`), Git reports a conflict on the
`.cfg`/XML text, exactly like code.

```bash
pkt resolve                     # report: what conflicts and where
pkt resolve --theirs            # accept the incoming branch
pkt resolve --ours              # keep the current branch
```

`pkt resolve` without a policy reports conflicted text and binary files,
including the first conflict-marker line for each text file, and exits non-zero
without modifying or staging anything.

With `--ours` or `--theirs`, the resolver:

1. Applies the chosen side to every conflicted text file.
2. Fails if any conflict marker remains.
3. Refreshes `configs/*.cfg` and `metadata/topology.json` for affected
   snapshots.
4. Rebuilds conflicted `.pkt`/`.pka` files from the resolved snapshot.
5. Stages only the resolved text paths, regenerated snapshot directories, and
   rebuilt binaries. It never runs a repository-wide `git add`.

A binary-only conflict rebuilds from the existing snapshot. If that snapshot is
missing, the resolver fails rather than inventing one.

The **decision** (whose VLAN wins) stays human; the mechanics are automated.

### Device-scoped manual alternative

When you need full control, edit only the snapshot and rebuild explicitly:

```bash
pkt edit snapshot/<project>/base.snapshot.xml \
    chgline SW_ACC_ADMIN_PUNO FastEthernet0/3 \
    " switchport access vlan 50" \
    " switchport access vlan 60"

pkt build snapshot/<project>/base.snapshot.xml topologia/<project>.pkt
git add snapshot/<project> topologia/<project>.pkt
git commit
```

The pre-commit hook warns whenever a snapshot is changed without its binary, so
this step is hard to forget even if you do not read this document.

### Rules for editing snapshots

- **Never** fix conflicts with global tools (`sed` over the whole XML, or any
  find-replace across the multi-megabyte document). Edits must be scoped to one
  device; use `pkt edit` (`show`, `setiface`, `chgline`, `insertafter`). A past
  incident where a global replace duplicated a VLAN assignment motivated this
  rule.
- Be explicit about the config block: `RUNNINGCONFIG` and `STARTUPCONFIG` are
  separate; `pkt edit` operates on the running config.
- `setiface` replaces the **entire interface block**; use `chgline` for
  surgical single-line changes and keep surrounding lines (`description`,
  `portfast`, …) that you did not intend to touch.
- `chgline` matches a complete line, including leading spaces. Zero matches
  fail; multiple matches fail as ambiguous.

## Migration from the Python Implementation

Repositories wired with the old Python hooks keep working only until those
hooks are replaced. To migrate:

```bash
# 1. Install the Go binary and confirm it runs.
pkt --version

# 2. Rewrite the repository hooks and attributes in place.
pkt init

# 3. Optional cleanup of the old interpreter/script keys.
git config --unset pktgit.py 2>/dev/null || true
git config --unset pktgit.script 2>/dev/null || true

# 4. Confirm the existing snapshot is still valid and rebuild its binary.
pkt sync snapshot/<project>
pkt build snapshot/<project>/base.snapshot.xml topologia/<project>.pkt
```

The snapshot layout and file names are unchanged. `pkt init` is idempotent, so
it is safe to rerun after moving the binary or changing machines.

## Small-Team Etiquette

- One logical change per commit (one device config, one VLAN, one subset of
  interfaces); the diff is the review, so keep it readable.
- Pull/merge before starting Packet Tracer work; PT has no merge intelligence
  of its own.
- Never edit `snapshot/` and `topologia/*.pkt` in PT at the same time as making
  textual edits; pick one source of change per commit session.
- The PT version is pinned team-wide (**9.0.1.0858**). Opening and resaving
  with a newer PT may produce a format variant the codec has not been verified
  against.
